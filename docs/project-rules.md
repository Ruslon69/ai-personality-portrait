# Правила проекта

Эти правила обязательны для продуктовых решений, дизайна и будущей разработки. Спорные решения отмечаются в документации как открытые вопросы и не считаются утверждёнными без решения владельца продукта.

## UX

- Интерфейс понятен без инструкции.
- Каждый экран содержит одно главное действие.
- Текста минимум: он помогает принять решение или выполнить шаг.
- Вопросы всегда имеют готовые варианты ответов.
- Собственный текст пользователя необязателен.
- Прохождение должно ощущаться лёгким и быстрым.
- Функции открываются постепенно, по мере появления ценности.
- Главную страницу нельзя перегружать.
- Мобильная версия проектируется наравне с десктопной.
- Пользователь всегда понимает текущий прогресс и следующий шаг.
- Результат должен быть удобным для сохранения и публикации.

## Визуальный стиль

- Современный, лёгкий и эмоциональный.
- Не детский и не медицинский.
- Не перегруженный эзотерикой.
- С мягкими, приятными анимациями.
- Анимации помогают интерфейсу: показывают переход, прогресс или результат, а не отвлекают.
- Никаких постоянных летающих элементов, навязчивых эффектов и визуального шума.

## Совместимость

- Результат строится через интересную инфографику и лёгкие интерактивности.
- Отдельные режимы для дружбы, романтических отношений или работы могут появиться позже.
- Нельзя утверждать, что пара обязана расстаться или точно подходит друг другу.
- Нужно показывать сильные стороны, различия, зоны напряжения и практические советы.
- Результаты должны быть бережными, полезными и оставлять решение за людьми.

## Безопасность и доверие

- Никаких психологических, медицинских или иных диагностических заключений.
- Никаких категоричных предсказаний.
- Эзотерические блоки явно обозначаются как интерпретации для развлечения и саморефлексии.
- Нельзя анализировать по голосу национальность, религию, сексуальную ориентацию, здоровье или политические взгляды.
- Голос нельзя использовать для идентификации человека.
- Исходная запись по умолчанию удаляется после анализа, если пользователь отдельно не выбрал сохранение.
- Обучение моделей на пользовательских данных возможно только при отдельном явном согласии.
- Пользователь может удалить профиль и все данные.
- Чувствительные данные не должны попадать в логи.
- Результаты сервиса нельзя использовать для решений о работе, кредитах, образовании или лечении.
- Необходимо ясно сообщать, какие данные используются, как долго они хранятся и как их удалить.

## Рабочий процесс

- Не начинать разработку без утверждённой документации.
- Не добавлять функции, которых нет в утверждённом MVP.
- Перед изменениями сначала изучать существующие документы.
- Изменения должны быть небольшими и проверяемыми.
- После выполнения задачи всегда предоставлять `SUMMARY`.
- Не выполнять Git commit без отдельной команды пользователя.
- Не устанавливать зависимости без явной необходимости.
- В рамках текущей задачи не создавать код приложения.

## Требования к документации

- Язык документов — русский.
- Формулировки ясные и профессиональные, без рекламного пафоса.
- Не использовать чрезмерно длинные абзацы.
- Использовать понятные заголовки.
- Не дублировать один и тот же текст во всех файлах: каждый документ отвечает за свою область.
- Спорные решения помечать разделом «Открытые вопросы».
